## 对比有效性(预检 cap 规则)

Cap 命中率(M0-T 47-50%、M0-J 56-67%、M1 33-39%)**全部超过 5% 阈值
——按预注册规则,本轮所有臂的对比无效**,数字仅作诊断。M1 中位 598
token 远低于 1070 预算却仍有 1/3 撞顶,说明部分输出不终止。

## 诊断(逐例核对,非猜测)

- **实体抽取已解决**: 模型输出的姓名/邮编逐字来自指令(如
  retail_17 的 Fatima Johnson/78712)——v1 的 user-latent 假象与
  v2 的幻觉担忧均未复现;
- **失败模式 = 计划不完整**: gold 需要 3 次 get_order_details 时
  模型只计划 1 次;需要 get_product_details 时整步缺失。调用数不足
  → 双射失败 → 全指标为 0;
- **根因 = 训练多样性不足(T8 已记录)**: v3 仅 2 种模板形状/130
  任务/单域,模型学会了两种形状并正确抽取实体与绑定语法(可解析
  输出中 runtime_ref 结构存在),但覆盖不了正式测试的形状空间。

## 下一步(v3.1 杠杆,按预期收益排序)

1. **模板多样化**: 多订单(1-4 次 get_order_details)、产品查询
   前缀、地址修改族、取消族;目标 ≥8 模板 × 300+ 任务;
2. **生成预算 3×max 重跑**(M0-J ~3600)使 cap<5%,对比才有效;
3. 共享盘上已有 Qwen2.5-**7B** 基座,可加 7B 臂看规模效应;
4. seeds 45/46 方差。

**诚实结论**: 端到端管线(数据→训练→冻结测试→scorer v3+CP CI)
首次全流程跑通;当前 3B×v3 在真实正式测试上 0%(A 条件 CI 上界
11.6%),瓶颈已从"绑定语法/实体抽取"收窄为"计划形状覆盖"——
这是数据问题,不是架构问题。
